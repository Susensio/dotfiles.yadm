description: Refresh pi's model catalog and propose model-alias.json and enabledModels updates
---
Refresh the model catalog and reconcile `~/.config/pi/agent/model-alias.json` and `enabledModels` in `~/.config/pi/agent/settings.json` with it. Read ADR-0103 first; it owns the rung ordering rules, ADR-0118 owns the quota arithmetic, and ADR-0123 how many Go rungs a tier may hold.

1. `pi update --models`, then `pi --list-models` for the current catalog.
2. Run `~/.config/pi/agent/bin/pi-model-cost` and read the table before proposing anything: it prices every Go model, so a model no tier names can still be the best answer the provider sells. The live multipliers, 5h drain and IPD override any prices or scores frozen in the `$comment`, which the last sync recorded and only that sync verified. An `intel` of `n/a` means there is no comparable composite, not that nothing is measured: read the `tb4/sci` columns beside it, never guess a score, and never re-normalise the index weights over a subset (ADR-0124). Record the index version line with any score you use.
3. Conditional rungs: any rung whose access is gated — a contributor variant, a training-class endpoint, a fork — is verified to answer with a one-token `pi -p --model <ref> ok` before the table is trusted, because the catalog keeps listing it after the gate closes. A rung that refuses leaves the chains and returns to `$bench` with the new condition.
4. Dead entries: every alias target and `enabledModels` entry (except `alias/*`) must exist in the catalog — the `model-drift` warning at startup names them too. A dead alias target fails its whole chain, so list these first with a replacement when one is obvious.
5. New models: for providers already used in the config, list models that no rung places, `enabledModels` enables or `$bench` records — the `model-drift` warning lists the same set at startup. Skip ones that are previews, embeddings, or otherwise unsuitable for an agent; say why. Place one in a tier only using the script's drain/IPD and the benchmark evidence it prints.
6. Show the proposed edits as a short list (entry, tier or list, reason, and the drain/IPD behind it) and wait for approval. Do not write anything before it.
7. After approval, edit both files, update the `$comment` read date and scores if you used new ones, and rerun `pi --list-models` to confirm every target resolves.
8. Keep `$bench` in `model-alias.json` complete: every model you priced, rejected or promoted gets an entry with why it is out and what would promote it — no numbers, since this run's table is the numbers. `pi-model-cost` warns about an enabled model that is neither placed nor benched, and a bench entry is the record a later sync checks before re-litigating a rejection.
